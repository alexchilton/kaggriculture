## 0. Headline, before the detail

The stall is real and I can name the line.
But the honest reading of the numbers is that **it is not lost work**, and the framing "we run out of
things to do" is exactly right in a way that makes the idle row the wrong thing to fix.

At hour 2 of day 10 -- the last crew-change replan -- `plan_routes` produced tours totalling
**195 turns against 273 turns of crew capacity**.
78 turns were surplus *at plan time*, before a single unit had moved.
Measured idle on the day is 72-73.
So the idle was not created by a scheduling failure during the afternoon; it was in the plan from
the morning, and no executor path can recover work that the node set never contained.

That does not make day 10 clean.
It relocates the defect: **12 melons and 2 fertilizer are still sitting in two hands at hour 23**,
and the mechanism that fails to deliver them is a different one from the mechanism that produces
the PASSes.

## 1. The mechanism, with the line

### 1a. Why a unit whose route empties never gets another node

`kagg/search/schedule_agent.py:683-704`, the `if idle:` top-up:

```python
        idle = [u for u in live if not routes.get(u, {}).get("route")]
        ...
        if idle:
            busy = _claimed_tiles(units, routes, idle, STEAL_MARGIN)
            ...
            sub = RT.plan_routes([units[u] for u in idle], nodes_for(busy),
                                 [budget[u] for u in idle], depots,
                                 {k: load[u] for k, u in enumerate(idle)}, supply=free)
```

with `nodes_for` at line 654:

```python
    def nodes_for(skip):
        return [n for n in RT.build_nodes(tiles, day, shed, carried, unlocked, pins, hour)
                if n.tile not in skip]
```

and `_claimed_tiles` at `schedule_agent.py:521`, whose `margin is None` branch is the whole story:

```python
    if margin is None:
        return set(claimed)
```

`STEAL_MARGIN = None` (`schedule_agent.py:344`).
The file's own docstring states the consequence: *"`None` disables stealing entirely and restores
the old rule, where every tile in a committed tour is off limits to everyone else for the rest of
the day."*

So the top-up offers the idle unit `build_nodes(...) minus every tile in any committed tour`.
The dawn plan distributed the whole node set across the crew, so that subtraction is total.

### 1b. Why it then emits PASS rather than walking anywhere

`schedule_agent.py:849`, the return leg, is the only thing that moves a unit with an empty route:

```python
        if act == ["PASS"] and not st["route"] and any(v > 0 for v in inv.values()):
```

The `any(v > 0 for v in inv.values())` gate is the line that produces the standing still.
Unit 0 DROPs its whole load at hour 9 and is therefore empty-handed from hour 10.
Empty hands + empty route + no offered node = `act = ["PASS"]`, unconditionally, for 14 turns.

## 3. Is this "stale budgets on committed tours"?

**No. It is a different thing, and it is not that trap in disguise.**

The trap named at `router.py:695-700` is: *"`budget` is `TPD - hour - 1` and only IDLE units are
replanned, so a unit committed at hour 6 keeps a tour costed against a budget that no longer
exists"*.

Measured here, the opposite holds for the units that go idle:

- Their budgets are recomputed fresh on every turn and are correct (§2a: 13, 12, 11, ...).
- Their tours do not overrun the budget -- they finish **early**, with 6-14 turns unspent.
- The units are idle because the node set is empty, not because a stale cost refused an insertion.

There is *one* place where §2 touches the stale-budget family: `u1`'s tour overrunning its own
closed cost by ~2 turns (§2e), which is a cost-accounting error on a committed tour. That is
adjacent to the trap but is not the trap -- the budget is not stale, the *service estimate* is
wrong. See §7.

The two reverted closed-tour attempts (`router.py:688-700`, `router.py:729-736`) both broke
`d3 sell 5/5 -> 3/5` by letting units range further out. Nothing proposed below changes any
insertion marginal, so that failure mode is not re-entered. Note however that §5's second option
does touch tour shape, and §6 says why that one is the risky one.

## 4. Proposed fix

Three separable things, in the order I would do them. Only the first is cheap and safe.

### Fix A (executor) -- a productive default for an empty-handed idle unit

`schedule_agent.py:849`. Widen the return-leg condition so an empty-handed unit with an empty route
walks to the nearest depot instead of passing:

- keep the existing DROP branch exactly as it is (goods in hand -> walk home -> DROP);
- add: if the route is empty and the hands are empty and the unit is not already at a depot,
  step toward the nearest depot.

Rationale, and it is deliberately modest: it cannot cost work, because those turns are provably PASS
today (§2c). What it buys is **position**. Every draw starts at a depot, so a crew that spends its
surplus standing at the shed begins the next replan -- and the next dawn -- from the tile that every
PICKUP needs. It also happens to move `_pass` toward `_move`, which is the tape's shape, but that is
a side effect and not the reason.

This belongs in the **executor**, not in `plan_routes`. It is a decision about what to do with turns
the planner has already declined to allocate; putting it in the planner would mean inventing
zero-prize nodes, which changes the insertion ranking for real work.

### Fix B (router, `build_nodes`) -- produce in a hand is a task

`build_nodes` emits nodes for board tiles and pins only. It has no node whose task is *"this
sellable is in a hand and the market cannot see it"*. Consequence measured in §2e.

The structural problem is that such a node is **unit-bound** -- only `u1` can deliver `u1`'s melons
-- and `plan_routes` has no representation for a node that only one vehicle may take. So this is
not a two-line change and I am not proposing it as the first move.

### Fix C (nothing to fix) -- the crew size

13 units for 37 nodes is the actual source of the 78 surplus turns. If the hire row comes from the
tape's schedule, this is not ours to change on this seed. Recording it so the next session does not
re-derive the idle row as a routing bug.

## 6. What it risks breaking

`d0-d5` currently read `7 6 4 7 7 7` and days are matched in order, so an early-day regression is
disqualifying.

**Fix A, the real risk, and it is not zero.** The branch only fires on turns that are PASS today, so
it cannot delete a work op *on the turn it fires*. But it moves the unit, and the unit's position is
an input to the **next** turn's planning in two places:

- `_claimed_tiles(units, routes, idle, margin)` measures `soonest` from `units[u]` -- inert while
  `STEAL_MARGIN is None`, so no exposure today, but it becomes live if stealing is ever re-enabled;
- `plan_routes(units=[units[u] for u in idle], ...)` costs every insertion from `units[u]`. A unit
  parked at the shed is nearer some nodes and further from others, so the very next top-up that
  *does* find a node can assign it differently.

That second one is the one to watch on d0-d3, where the crew is small, the top-up path is
load-bearing (the `STEAL_MARGIN` docstring records d0 replans firing at hours 9, 14, 15, 16, 17, 18),
and `d3 sell 5/5` is the fragile cell that both reverted closed-tour attempts broke. Run
`--days 11 --diff` and check `d0..d5` before looking at `d10`.

**Fix B** touches the ferry/DROP path, which `CLAUDE.md` and `schedule_agent.py:820-848` both record
as having cost **$15,272 over twelve seeds** when done broadly ("drop the surplus whenever standing
on the shed") and as having broken
`test_wheat_already_in_a_hand_feeds_the_herd_with_an_EMPTY_shed`. It also interacts with the
`FEED_DAYS * alive` wheat reserve, which is described as the self-healing material the `if idle:`
top-up replans from. Any delivery node must exclude wheat the crew is carrying for its own FEED
stops, exactly as `DELIVER_THE_SELL_ROW` already does.

## 7. Uncertainty, stated plainly

The §1/§2 mechanism for the PASSes is not in doubt: `nnodes=0` on every top-up call from h10 to h23
is a measurement, not an inference.

What I have **not** isolated is §2e -- why `u1`'s tour, planned at closed cost 21 against a budget of
21, spent 15 turns reaching its last stop and then needed 8 more to walk home. Two candidates
remain:

1. **`Node.service` under-counts.** `service = len(ops)` is fixed at plan time, but the executor
   re-derives ops at the tile via `_live_ops` against the *live* board and only pops the node when
   that returns empty. A tile planned as `WATER` alone can, by the time the unit arrives, also offer
   `HARVEST` -- two turns spent against one costed. Every such tile silently overruns the tour.
2. **`homeward` is measured from the wrong tile.** It takes `min(dist(route[-1].tile, d))` over the
   final route, but `_two_opt` reorders afterwards and the closing correction at `router.py:880` is
   recomputed from `ordered[-1]`. If a stale stop is popped mid-day the tour's real last tile is not
   the one the reserve was priced from.

**The one measurement that separates them:** log, per node, `n.service` at commit time against the
number of turns the executor actually spends standing on that tile before popping it. If the two
diverge on any node in `u1`'s tour, it is (1). If they agree and the shortfall is entirely in the
final walk, it is (2). That is a ten-line addition to the same probe and it should be done before
anything in §4 is written, because (1) would mean every tour on every day is under-costed and that
is a much larger finding than day 10.
